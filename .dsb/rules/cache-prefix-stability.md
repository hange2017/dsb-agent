# 缓存前缀稳定性基本规则（工程强制约束）

> 生成时间：2026-08-11
> 适用范围：**所有改动 `system prompt` / 压缩块 / `tail` / 工具定义 / 历史消息序列（message list）构造方式**的代码变更。
> 依据：DeepSeek 独立缓存前缀单元机制（请求边界落盘 / 公共前缀检测 / 固定 token 间隔落盘），详见 `.dsb/docs/2026-08-11-缓存前缀稳定性优化清单.md`。
> 目的：保证「system + tools + 历史 messages」的前缀字节跨轮稳定，最大化缓存命中率，避免缓存雪崩。

---

## 一、缓存机制三原则（不可违反）

1. **完整匹配**：每条缓存前缀是独立完整单元，任何一字差异都会让该单元失效 → **前缀的一字节变化 = 整段 miss**。
2. **前缀稳定**：system prompt、工具定义 JSON、历史消息字节必须跨轮稳定才能命中。
3. **公共前缀检测**：多次请求间存在公共前缀时会被作为独立单元落盘 → **变化点越靠后，前面稳定段越能命中**。

---

## 二、基本规则（改动 system/压缩块/tail/messages 时必须遵守）

### 规则 1：system prompt 会话内必须字节稳定 🔴
- system 中**禁止**放入会话内会发生变化的动态内容（todo 清单、实时状态等）。
- 易变内容应放到 **messages 尾部**（尾部追加不影响前缀）。
- 会话创建的只读内容（memoryIndex、dreamHint、rules、工具定义等）在会话内构建一次后**不得再变**。
- ✅ 已落地：todo 清单已移出 system，仅当非空时注入请求包尾部（`agentLoop.ts` `injectTodoIntoMessages`）；空清单不注入，避免尾部膨胀。

### 规则 2：工具定义顺序跨轮稳定
- 工具 def 数组（内置 toolDefs + MCP 插入序 + plugin）在会话内顺序**不可打乱**、不可中途增删（无重启场景）。
- 新增工具 -> 在消息层追加说明即可，不要塞进 system。

### 规则 3：历史消息只追加、尾部变化，永不重写
- messages 只能 `push`（尾部追加）；已写入中部/前缀的消息**不得原地改写、删行、重排**。
- 中部消息字节变化 = 后续全部前缀断裂，一律禁止。
- 若某消息内容会因后续处理而变化，必须在**写入 messages 前就按最终策略定型**（写前定型），禁止「先原始后精简」两种形态。

### 规则 4：压缩块「只追加、只删尾」🔴
- 压缩块属于 messages 前缀头部，重建/重排/中间删行 = 整块前缀断裂（= 缓存雪崩）。
- **新增内容只追加到 section 末尾**；旧行永不重写。
- **裁剪只删尾部**，禁止从中间摘行。
- section 标题要**恒输出**（空 section 用固定占位行，保持行位置永久固定）。
- 推荐「稳定段 + 增量段」双段结构：旧摘要永不重写，新摘要追加，超限只裁增量段尾部。

### 规则 5：不从此前已发送的消息中删中部块
- 消费后块删除（如 `trimConsumedToolUses`）若删**中部**已发送的 tool_use → 前缀断裂。
- 中部块尽量保留（token 成本换命中率）；只在压缩时集中清理，或只删尾部块。

### 规则 6：同一内容只允许一种字节形态
- 一条消息（tool_result、user 提示等）在发送给 provider 前后字节必须一致，禁止发送前做改变字节内容的转换（summarize / trim / 脱敏重写）。
- 内容需要精简时，在**写入 messages 前就完成**，发送前只做兜底同形态转换（不改字节）。

## 三、缓存杀手清单（改动时的避让参考）

| 场景 | 为何是杀手 | 正确做法 |
|---|---|---|
| todo 块放 system | 清单状态每轮变 → system 中部断裂 | 移出 system，放 messages 尾部 upsert |
| 压缩块整块重建 | messages 前缀头部重写 → 雪崩 | 只追加、只删尾、标题恒输出 |
| tool_result 发送前精简 | 同一内容两形态 → 后续轮断一次 | 写前定型 |
| 中部消费块删除 | 后续消息整体前移 → 前缀断裂 | 保留中部，只删尾部 / 压缩时集中清理 |
| MCP 工具动态注册 | 工具定义 JSON 变化 → 断裂 | 会话内不重启 MCP；工具集视为只读 |

## 四、验证要求（改动后必做）

- 影响 system / 压缩块 / tail / messages 构造的改动，跑 `python3 scripts/analyze-cache-prefix.py` 对比改前改后：
  - 稳定期命中率（当前基线 68~75%）
  - 压缩后首轮命中率（当前 ~10%）
  - compacted / thinking / tail 三组分别对比。
- 对账：`provider_round.cacheReadTokens` 与官方数据小时级对账（口径见 `.dsb/docs/2026-08-10-压缩成本与缓存雪崩分析.md`）。
- 不降命中率是硬性验收；有例外需在 PR 说明理由并量化影响。
