## 数据校验强制流程(一切结论的前提)

> ⚠️ **这是最高优先级工作流纪律(用户 2026-08-10 晚明确要求)**:
> 一切统计记录与结论成立的基础,是**本地统计的每类 token 消耗与官方数据高度吻合**。

**每次统计 / 记录数据 / 下结论之前,必须执行:**

1. **先问用户要官方数据**:请求用户提供与本地统计**同一时段**的官方三类 token
   (输入命中 / 输入未命中 / 输出)+ 单价;
2. **逐项对账**:本地 vs 官方,命中 / 未命中 / 输出三项逐一比较,计算偏差百分比;
3. **判定偏差阈值**:
   - 命中 / 未命中偏差 < 5% → 数据可信,可继续分析;
   - 偏差 5-15% → 部分统计盲区,需定位缺口后修正,暂缓下结论;
   - 偏差 > 15% → 存在系统性盲区(如压缩 LLM 调用未记录),必须先补统计再下结论;
4. **对账通过后才允许**:记录结论、写入文档、调整策略参数、给出优化建议。

> 偏差即盲区,盲区即下一步统计扩展的优先级。

## 一、三个问题的批判性回答

### 1. 窗口小 vs 窗口大:漏掉了「未命中成本」这个关键维度

| | 窗口小 | 窗口大 |
|---|---|---|
| 每轮输入 token | ✅ 少 | ❌ 多 |
| 压缩频率 | ❌ 频繁 | ✅ 少 |
| **缓存命中率** | ❌ 差(频繁压缩→前缀常变→缓存失效) | ✅ 好(前缀稳定) |

关键:成本大头不是「输入的 token 量」,而是「**未命中的 token 量**」。
命中 0.02 元 vs 未命中 1.0 元,差 **50 倍**。一次压缩让下轮 5 万 token 全部 miss
要花 5 分,抵得上 25 轮大窗口的命中输入。

### 2. 定价理解 ✅ 正确,且这是全局最重要的数字

今日实测(修正口径:inputTokens=未命中,cacheRead=命中,二者并列):

```
总真实输入: 32.7M tokens(命中 28.3M,未命中 4.4M)
缓存命中率: 86.7%
常规轮次成本: ¥5.28 = 命中 ¥0.57 + 未命中 ¥4.36 + 输出 ¥0.35
```

**未命中只占 13.3% 的量,却贡献 82% 的成本**。优化目标 = 提高命中率、减少未命中,
而不是减少 token 总量。

### 3. 加大窗口 → 降本 + 提速 + 提高命中率?方向对,但有两个误区

- ✅ 减少压缩次数 = 省压缩自身 LLM 成本 + 省缓存失效成本
- ⚠️ 误区一:「加大窗口提高命中率」因果错了。命中率取决于**前缀稳定性**,
  不是窗口大小。正确因果链:加大窗口 → 减少压缩 → 前缀更稳定 → 命中率提高。
- ⚠️ 误区二:窗口越大,单次 miss 惩罚越重(256K 窗口 miss 一次 = ¥0.26,64K 仅 ¥0.06)。

最优解不是「无限加大窗口」,而是 **「稳定前缀 + 少而轻的压缩」**。

## 二、关键数据证据

### 1. 交叉验证:本地统计 vs 官方(18:00-19:00)

| 指标 | 本地 | 官方 | 差异 |
|---|---|---|---|
| 输入(命中) | 16,893,184 | 16,996,864 | -0.6% |
| 输入(未命中) | 2,524,249 | 2,619,799 | -3.7% |
| 输出 | 98,537 | 153,085 | **-35.6%** ⚠️ |

**差异本身就是证据**:输出差 54,548(35.6%)几乎全部来自**压缩的 summarize 调用未被记录**
(8 次压缩 × 每次 2-3 次 LLM 调用)。未命中差 95,550 ≈ 压缩自身 LLM 的输入(≈53K × 2 次)。
→ **压缩的 LLM 调用是统计盲区,它消耗的 token/费用没进任何账本。**

### 2. 官方 18:00-19:00 成本账

| 项 | tokens | 单价 | 成本 |
|---|---|---|---|
| 输入(命中) | 16,996,864 | 0.02/M | ¥0.34 |
| 输入(未命中) | 2,619,799 | 1.0/M | **¥2.62** |
| 输出 | 153,085 | 2.0/M | ¥0.31 |
| **合计** | 19,769,748 | | **¥3.27** |

未命中占输入量 13.4%,却贡献 **80.2% 成本**。

### 3. 压缩后缓存雪崩(时间线铁证)

18:00-19:00 共 8 次压缩,每次后出现同一模式:

```
压缩前:  命中率稳定 92-94%,每轮未命中 ~5-6K   ← 基线
压缩后第一轮: 命中率 4-8%!未命中 75-86K      ← 雪崩(整段缓存失效)
随后 10-20 轮 / 1-2 分钟:未命中逐步降回 ~5K   ← 缓存重建
```

每次压缩雪崩 ≈ 160K 额外未命中 ≈ **¥0.16**;
8 次压缩雪崩 ≈ 1.28M 未命中 ≈ **¥1.28,占该小时未命中成本的 ~49%**。

**即:该小时近一半的「未命中成本」是压缩造成的,而非对话本身。**

### 4. 输入构成:压缩块占 37%

| 构成(平均每轮 45,690 tokens) | tokens | 占比 |
|---|---|---|
| tail(最近 70-79 条消息原文) | 18,070 | 39.6% |
| **compacted block(历史压缩摘要)** | **17,056** | **37.3%** |
| toolResult(工具结果) | 10,539 | 23.1% |
| thinking block(推理脉络) | 6,995 | 15.3% |
| system | 3,569 | 7.8% |

压缩块质量 = 模型能看到的历史质量。压缩丢关键决策/文件路径 → 后续所有轮次在残缺历史上工作,
这是压缩的**隐性正确性成本**,比 token 成本更致命。

## 三、压缩有效性三层框架

| 维度 | 度量 | 现状 |
|---|---|---|
| **token 效率** | before/after 比率(信息密度) | ✅ 已有数据(今日 21.2% 缩减) |
| **成本效率** | 每保留 1K 有效信息的钱(含雪崩) | ❌ 未记录(压缩自身 LLM 无 usage) |
| **信息保真** | 压缩后关键信息是否可召回 | ❌ 完全未度量(影响正确性,最易被忽略) |

信息保真测试思路:
1. **自动 QA 抽查**:压缩后随机抽 `[r{n}]` 序号,用 LLM 问该序号对应的决策/文件路径,
   看压缩块能否回答 → 保真率打分
2. **任务成功率关联**:记录任务完成/失败,与压缩频率、压缩块大小做相关性分析
3. **召回测试**:压缩后 ContextRecall 查已知事实看是否命中(冷存储天然适合)

## 五、用户大策略确认与落地(2026-08-10 晚)

> 用户拍板四个大方向,下文是每个方向的落地细化。

### 方向 1:官方每小时 token 数据 + 成本优化目标

- **数据供给**:用户可提供每小时官方三类 token(命中/未命中/输出)+ 单价 → 作为对账基准。
- **优化目标函数**:`总成本 = 未命中×1.0 + 命中×0.02 + 输出×2.0`(元/M)。
- **策略空间**:适度提高输入总 token 提高命中比例 → 降未命中 → 总成本下降;
  但输入非免费(命中 0.02/M、未命中 1/M),存在**成本最优拐点**,不是窗口越大越好。
- **落地**:
  - 建「小时对账表」:本地汇总 vs 官方,偏差定位统计盲区;
  - 跑不同窗口(64K/128K/256K)各若干小时,用官方数据画「窗口-小时成本」曲线找拐点。

### 方向 2:统计信息完善 + 可选开关

- **原则**:测试优化阶段,统计尽量完善充足,帮助定位问题;**做成可选配置,优化完成后可关闭,减少落盘**。
- **落地**:
  - 新增配置 `dsbAgent.stats.enabled`(默认开)与 `dsbAgent.stats.detailLevel: "minimal" | "full"`;
  - `minimal`:只记 provider_round / compaction / daily_cost(低成本、可长开);
  - `full`:打开 provider_send 逐类明细 + provider_send_detail + 压缩逐位置明细(仅测试期开);
  - 所有统计走现有 StatsStore,关闭后不再写 JSONL,零开销。
- **核心要求**:每次发给大模型的消息是**结构化的**,要对**每种信息逐类统计**;
  **特别是压缩时,每种压缩动作都要统计压缩时间 + 是否调用大模型**。

### 方向 3:以 64K 窗口为基准快速迭代,以小时为分析单元

- **现状**:64K 历史预算能完成各类编程任务,且**快速触发压缩** → 测试样本密集,统计收敛快。
- **意义**:以小时为分析基本单元成立,**不需要以天为单位的长期测试** → 迭代周期大幅缩短。
- **落地**:
  - 默认测试窗口定为 **64K**(`historyTokenBudget = 64000`);
  - 每个实验跑 1-3 小时即可评估(压缩触发频繁,样本量足够);
  - 实验矩阵:窗口大小 × 压缩策略 × 触发比例,每格 1-2 小时,快速对比。

### 方向 4:压缩「方法优化 + 策略优化」双轨结合

- **方法优化(压缩更快/更便宜)**:
  - B1 多路并行(3 个 LLM 调用 Promise.all);
  - B2 增量压缩; B3 分级压缩(算法裁剪 + LLM 精压); B4 预算内智能裁剪。
- **策略优化(减少雪崩危害)**:
  - **B7 压缩后灌回原信息**:压缩完成后,把压缩前的高价值信息以若干轮「补充提示」的形式
    随后续对话继续发给模型(等价于渐进式过渡),避免「一刀切替换前缀」导致的缓存全失效;
    同时也让模型在过渡期仍能看到关键原文,降低信息断层。
  - B5 动态触发(雪崩后冷却); B6 压缩后缓存预热; C2 前缀稳定设计。
- **结合方式**:方法优化解决「单次压缩的成本与耗时」,策略优化解决「压缩带来的系统级
  (缓存/信息连续性)冲击」,两者互补,不是二选一。

## 六、核心结论

1. **成本大头是「未命中输入」(80%)和「输出」(仅 10%)**,压缩是未命中的最大制造者
   (今日 18-19 点 ≈49% 未命中来自压缩雪崩)
2. **压缩有效性 = 信息保真 ÷ 总成本**,目前只度量了 token 效率,完全没度量信息保真
3. **「加大窗口」只是中间手段**,真正的目标是「减少压缩次数 + 每次压缩更便宜 + 压缩后缓存快速恢复」
4. **最有价值的三个实验**:B1 并行化(快)、C1 窗口成本模型(省)、A5 保真 QA(准)
   ——分别对应「时间、钱、正确性」
5. **用户拍板的方向**:以 64K 窗口为基准 + 小时为分析单元快速迭代;统计做成可开关;
   压缩走「方法(并行/增量)+ 策略(灌回原信息/缓存预热)」双轨。
