## 二、第九轮附带修复:续写提示污染需求轨

**现场证据**:本轮采样时,实时任务锚里地图 `**最新要求**` 行内容竟是
`[续写] 上一轮输出因长度上限中断…` —— 即 `maxTokensContinue` 注入的运行时合成 user 消息。

**根因**:`contextManager.ts` 抽轨时对**任意** user 文本都 `demands.push`;
而续写提示正是以 `{ role:"user", content: kMaxTokensContinueUserText }` 落盘(`agentLoop.ts`)
→ 进需求轨,并顶掉地图「最新要求 / 下一步」位,**反过来加重目标语义污染**。

**修法**(`contextManager.ts`):
- `isRuntimeContinueMessage`(判 `[续写]` 前缀)入轨前 `continue`;
- `INTERRUPTED_ASSISTANT_TEXT`(`[输出中断]`)不参与结论/解释轨;
- `isRuntimeSyntheticText` 在 `buildResidentMap` 重建地图时**剔除历史遗留**的污染条目
  (累积式会「粘住」旧条目,必须显式过滤 —— 否则旧会话的 `[续写]` 行会一直留在「近期需求」段)。

**测试**:`contextManager.test.ts` 增 2 例(续写提示不得出现于块、地图最新要求须为真实最后需求、
历史遗留污染条目被剔除)。

### 二补:第 40 轮补漏 —— 前缀感知判定 + 地图全来源过滤

**现场证据**:实施后实时任务锚里,地图「近期需求」**和「下一步」两段都仍残留** `[续写] …` 行。

**根因(两处)**:
1. **判定漏判**:历史落盘的轨行形态是 `- [rN] [续写] …`(带编号前缀),
   而旧 `isRuntimeSyntheticText` 只 `startsWith("[续写]")` → **匹配不到**,污染行被放行。
   更隐蔽的是 `extractMapSectionItems` 会剥掉 `- ` 但仍留 `[rN]`,正则若强制要求 bullet 前缀同样漏判。
2. **过滤不全**:`buildResidentMap` 里 `goal / latestGoal / olderMiddle` 直接取自 `parts.demands`,
   上一版只过滤了 `prevRecent`(累积段)→ 污染行经 `mergeCompactedTracks` 持久化在需求轨,
   会继续占据「目标 / 最新要求 / 近期需求 / 下一步」位,反过来**污染目标语义**。

**修法**:
- `isRuntimeSyntheticText` 改为**前缀感知**:先剥 `[-*] ` 与 `[rN] `(二者均**可选**)再判前缀;
- `buildResidentMap` 对 `demands` 及 `latest()`(ledger/conclusions 来源)统一 `.filter(!isRuntimeSyntheticText)`,
  覆盖地图**全部五个段**的所有来源。

**测试**:`contextManager.test.ts` 再增 1 例 —— 轨行形态 `- [rN] [续写] …` + 裸 `[输出中断]` 的
demands/conclusions/prevMap 三来源同测,断言三形态均被剔除、真实需求仍在。

**生效时机**:旧会话**已落盘**的压缩块地图段不会被原地改写;`buildResidentMap` 只在**下一次压缩**时
用当前轨道重建 → 重载窗口后再次触发压缩,残留行即清。

→ 结论:修复代码**从未被"压缩"这个动作触发过**,落盘块仍是旧代码产物。

**同时暴露第二个缺口**:`[续写]` 不止在地图段,还作为**轨行**存在于 `## 需求` 轨
(`- [r125] [续写] …`、`- [r129] [续写] …`)。`mergeCompactedTracks` 会把旧块轨行**一路向前合并**,
**即使下次压缩把地图洗干净,这两行垃圾也永远不会消失** —— 等于每次压缩都向模型复述一遍

**修法**(`contextManager.ts` 的 `compact()`):合并后、建图前,对**四条轨**
(`demands` / `conclusions` / `explanations` / `ledger`)统一 `.filter(!isRuntimeSyntheticText)`。
新消息已在 `stratify` 入轨前被 `isRuntimeContinueMessage` 拦截 → 这是一次性清理,
稳态下过滤结果与输入内容相同(字节不变),仅在首次清理时改动一次。

**测试**:`contextManager.test.ts` 增 1 例 —— 构造「旧代码产出的」污染块(需求轨含合成行、
结论轨含 `[输出中断]`)作为 `messages[0]`,压缩后断言:合成行**在整块范围内**消失,
而真实需求/结论/新需求**全部保留**。

**反证(证明该用例有效)**:临时把 `purged` 退回 `merged`,单跑该用例 → **失败**,
报 `expected '[前文摘要]\n[compacted]\n## 任务地图\n**目标:**…' not to contain '[续写]'`;
还原后 **通过**。排除"测试恒真"。

## 三、阶段 C(96k / 3:7)预算实测结论

用户把历史预算改为 **96K、3:7 开**(compacted : tail),自 2026-09-14 23:01:40 起,
并要求记录时间点、后续统计是否加剧。采样于同日 23:46,与阶段 B(64K、.56/.44)**同一会话自然对照**。

### 关键数据(每轮)

用 `effCostIdx = input + 0.1×cacheRead + output`(缓存感知成本指数):

| 指标(每轮) | 阶段 B(64K,.56/.44) | 阶段 C(96K,.30/.70) | 变化 |
|---|---|---|---|
| avgInput(cache miss,最贵) | 2444 | 3561 | **+45.7%** |
| avgCacheRead | 44380 | 60088 | +35.4% |
| avgOutput | 830 | 1677 | +102% |
| **effCostIdx** | **7712** | **11242** | **+45.8%** |
| 约合 $/round(Sonnet 3/15/0.3) | 0.0331 | 0.0539 | **+62.9%** |
| 请求 avgTotal | 34239 | 53054 | +55% |
| 请求 **avgTail** | 16427 | 35337 | **×2.15(主因)** |
| 请求 avgBlock | 15649 | 15311 | −2% |
| compaction / 千轮 | 81.4 | 41.5 | **−49%** |
| 压缩自耗 token/轮 | 12 | 25 | +13 |

### 结论

1. **token 消耗确实加剧**:每轮成本 +45.8%(成本指数)/ +62.9%($)。
2. **主因是 tail 变长**:3:7 把 tail 触发点 21120 → 50400,每轮多带 2.15× tail;
   compacted 目标虽降到 14400,实测块基本持平。
3. **收益是压缩频率减半**(81.4 → 41.5 次/千轮),但压缩本身极便宜(12→25 tok/轮),
   **省下的抵不上每轮多带的 tail**。
4. **最大不确定项是 output 翻倍**:更可能是任务强度混淆(B 诊断/读码,C 密集改文件),
   非参数直接导致;但 output 单价最高,放大了总成本。
5. **不可误读的口径**:`inputTokens / 用户轮` 看似减半,但同期 `rounds / 用户轮` 也从 75→28,
   需相除才可比,**不可单独采信**。

### 建议

- **口径**:以 `effCostIdxPerRound`(或 $/round)为准,勿比总和;要干净结论需
  **另起两次全新会话各跑 N 轮**同任务对比。
- **参数**:成本敏感可回 `.40/.60`(tail 触发点约 28800)折中;若以「少压缩、少漂移」为先,保持 3:7 可接受。
- **值得单独优化**:output 翻倍若确认非任务混淆,应查「tail 越长 → 模型是否输出更长」的因果。

### 测量脚本

`.dsb/docs/compaction/budget-measure.ps1` 本轮修两处:
① 新增 `effCostIdxPerRound`;② 修好 reason 分组(原取 `$_.reason` 恒空,应为 `$_.data.reason`)。

## 六、三补(2026-09-15):地图「下一步」不再冒充待办

### 现场问题

重载后的旧会话地图里出现:

```
### 下一步
- 实测其可达性与拦截效果(1 or 2)
- ...
```

这些条目实际上是**已实现过的建议**(P2-3 块首地图之类),却被列为"下一步"→ 语义错误,
会把**已完成**事项显示成待办,诱导模型重复劳动。

### 根因

`contextManager.buildResidentMap` 用**需求轨的较早中间需求**填 `next`:

```ts
next: latest(olderMiddle, 2),   // 历史需求 → 冒充「下一步」
```

历史需求**没有完成度信息**,而压缩块又访问不到 `TodoManager` → 块内无论怎么填都不可能
得到真实的"下一步"。这属于"用一个必然错误的来源去满足一个需要精确状态的位置"。

### 修法(方案 A:让来源与语义对齐,而非强行猜)

| 位置 | 改动 |
|---|---|
| `taskMap.ts` | 新增 `earlierDemands` 字段 + `EARLIER_DEMANDS_TITLE = "更早的需求"`;段序:…/近期需求/更早的需求/已做/结果/下一步。`next` 注释收紧为"**真实**未完成事项";新增 `next` 的 doc 警告(不得用历史需求充当) |
| `contextManager.ts` | `buildResidentMap`:`next: latest(olderMiddle, 2)` → `earlierDemands: latest(olderMiddle, 2)`;块内**不再输出**「下一步」段(文档注释同步) |
| `agentLoop.ts` | 新增 `NEXT_STEP_TITLE = "### 下一步"`、`buildNextStepSection(pending)`(去空白、≤3 条、空则返回 `""`);`buildTaskAnchor(todoBlock, mapLines, pendingTodos)`;`injectTodoIntoMessages` 新增 `opts.pendingTodos`;调用点传 `this.todo.list().filter(i => !i.done).map(i => i.content)` |
| `contextCompactor.ts` / `configuration.ts` / `project-overview.md` | 文档注释中「目标/已做/结果/下一步」→ 去掉「下一步」并说明由任务锚注入 |

任务锚新形态(仅请求视图,不进历史;变化点仍在消息尾部 → 前缀可缓存):

```
〔任务锚〕按下面清单继续推进;需要更早的历史原文时,用 ContextRecall(seq=n) 回查压缩块中的 [r{n}] 行。
### 下一步
- <真实未完成 todo 1>
- <真实未完成 todo 2>
## 任务地图
**目标:** … / **最新要求:** … / ### 近期需求 / ### 更早的需求 / ### 已做 / ### 结果
## 任务清单
- [x] 已完成
- [ ] 未完成
```

## 二、第九轮附带修复:续写提示污染需求轨

**现场证据**:本轮采样时,实时任务锚里地图 `**最新要求**` 行内容竟是
`[续写] 上一轮输出因长度上限中断…` —— 即 `maxTokensContinue` 注入的运行时合成 user 消息。

**根因**:`contextManager.ts` 抽轨时对**任意** user 文本都 `demands.push`;
而续写提示正是以 `{ role:"user", content: kMaxTokensContinueUserText }` 落盘(`agentLoop.ts`)
→ 进需求轨,并顶掉地图「最新要求 / 下一步」位,**反过来加重目标语义污染**。

**修法**(`contextManager.ts`):
- `isRuntimeContinueMessage`(判 `[续写]` 前缀)入轨前 `continue`;
- `INTERRUPTED_ASSISTANT_TEXT`(`[输出中断]`)不参与结论/解释轨;
- `isRuntimeSyntheticText` 在 `buildResidentMap` 重建地图时**剔除历史遗留**的污染条目
  (累积式会「粘住」旧条目,必须显式过滤 —— 否则旧会话的 `[续写]` 行会一直留在「近期需求」段)。

**测试**:`contextManager.test.ts` 增 2 例(续写提示不得出现于块、地图最新要求须为真实最后需求、
历史遗留污染条目被剔除)。

### 二补:第 40 轮补漏 —— 前缀感知判定 + 地图全来源过滤

**现场证据**:实施后实时任务锚里,地图「近期需求」**和「下一步」两段都仍残留** `[续写] …` 行。

**根因(两处)**:
1. **判定漏判**:历史落盘的轨行形态是 `- [rN] [续写] …`(带编号前缀),
   而旧 `isRuntimeSyntheticText` 只 `startsWith("[续写]")` → **匹配不到**,污染行被放行。
   更隐蔽的是 `extractMapSectionItems` 会剥掉 `- ` 但仍留 `[rN]`,正则若强制要求 bullet 前缀同样漏判。
2. **过滤不全**:`buildResidentMap` 里 `goal / latestGoal / olderMiddle` 直接取自 `parts.demands`,
   上一版只过滤了 `prevRecent`(累积段)→ 污染行经 `mergeCompactedTracks` 持久化在需求轨,
   会继续占据「目标 / 最新要求 / 近期需求 / 下一步」位,反过来**污染目标语义**。

**修法**:
- `isRuntimeSyntheticText` 改为**前缀感知**:先剥 `[-*] ` 与 `[rN] `(二者均**可选**)再判前缀;
- `buildResidentMap` 对 `demands` 及 `latest()`(ledger/conclusions 来源)统一 `.filter(!isRuntimeSyntheticText)`,
  覆盖地图**全部五个段**的所有来源。

**测试**:`contextManager.test.ts` 再增 1 例 —— 轨行形态 `- [rN] [续写] …` + 裸 `[输出中断]` 的
demands/conclusions/prevMap 三来源同测,断言三形态均被剔除、真实需求仍在。

**生效时机**:旧会话**已落盘**的压缩块地图段不会被原地改写;`buildResidentMap` 只在**下一次压缩**时
用当前轨道重建 → 重载窗口后再次触发压缩,残留行即清。

## 三、阶段 C(96k / 3:7)预算实测结论

用户把历史预算改为 **96K、3:7 开**(compacted : tail),自 2026-09-14 23:01:40 起,
并要求记录时间点、后续统计是否加剧。采样于同日 23:46,与阶段 B(64K、.56/.44)**同一会话自然对照**。

### 关键数据(每轮)

用 `effCostIdx = input + 0.1×cacheRead + output`(缓存感知成本指数):

| 指标(每轮) | 阶段 B(64K,.56/.44) | 阶段 C(96K,.30/.70) | 变化 |
|---|---|---|---|
| avgInput(cache miss,最贵) | 2444 | 3561 | **+45.7%** |
| avgCacheRead | 44380 | 60088 | +35.4% |
| avgOutput | 830 | 1677 | +102% |
| **effCostIdx** | **7712** | **11242** | **+45.8%** |
| 约合 $/round(Sonnet 3/15/0.3) | 0.0331 | 0.0539 | **+62.9%** |
| 请求 avgTotal | 34239 | 53054 | +55% |
| 请求 **avgTail** | 16427 | 35337 | **×2.15(主因)** |
| 请求 avgBlock | 15649 | 15311 | −2% |
| compaction / 千轮 | 81.4 | 41.5 | **−49%** |
| 压缩自耗 token/轮 | 12 | 25 | +13 |

### 结论

1. **token 消耗确实加剧**:每轮成本 +45.8%(成本指数)/ +62.9%($)。
2. **主因是 tail 变长**:3:7 把 tail 触发点 21120 → 50400,每轮多带 2.15× tail;
   compacted 目标虽降到 14400,实测块基本持平。
3. **收益是压缩频率减半**(81.4 → 41.5 次/千轮),但压缩本身极便宜(12→25 tok/轮),
   **省下的抵不上每轮多带的 tail**。
4. **最大不确定项是 output 翻倍**:更可能是任务强度混淆(B 诊断/读码,C 密集改文件),
   非参数直接导致;但 output 单价最高,放大了总成本。
5. **不可误读的口径**:`inputTokens / 用户轮` 看似减半,但同期 `rounds / 用户轮` 也从 75→28,
   需相除才可比,**不可单独采信**。

### 建议

- **口径**:以 `effCostIdxPerRound`(或 $/round)为准,勿比总和;要干净结论需
  **另起两次全新会话各跑 N 轮**同任务对比。
- **参数**:成本敏感可回 `.40/.60`(tail 触发点约 28800)折中;若以「少压缩、少漂移」为先,保持 3:7 可接受。
- **值得单独优化**:output 翻倍若确认非任务混淆,应查「tail 越长 → 模型是否输出更长」的因果。

### 测量脚本

`.dsb/docs/compaction/budget-measure.ps1` 本轮修两处:
① 新增 `effCostIdxPerRound`;② 修好 reason 分组(原取 `$_.reason` 恒空,应为 `$_.data.reason`)。

## 六、三补(2026-09-15):地图「下一步」不再冒充待办

### 现场问题

重载后的旧会话地图里出现:

```

- 实测其可达性与拦截效果(1 or 2)
- ...
```

这些条目实际上是**已实现过的建议**(P2-3 块首地图之类),却被列为"下一步"→ 语义错误,
会把**已完成**事项显示成待办,诱导模型重复劳动。

### 根因

`contextManager.buildResidentMap` 用**需求轨的较早中间需求**填 `next`:

```ts
next: latest(olderMiddle, 2),   // 历史需求 → 冒充「下一步」
```

历史需求**没有完成度信息**,而压缩块又访问不到 `TodoManager` → 块内无论怎么填都不可能
得到真实的"下一步"。这属于"用一个必然错误的来源去满足一个需要精确状态的位置"。

### 修法(方案 A:让来源与语义对齐,而非强行猜)

| 位置 | 改动 |
|---|---|
| `taskMap.ts` | 新增 `earlierDemands` 字段 + `EARLIER_DEMANDS_TITLE = "更早的需求"`;段序:…/近期需求/更早的需求/已做/结果/下一步。`next` 注释收紧为"**真实**未完成事项";新增 `next` 的 doc 警告(不得用历史需求充当) |
| `contextManager.ts` | `buildResidentMap`:`next: latest(olderMiddle, 2)` → `earlierDemands: latest(olderMiddle, 2)`;块内**不再输出**「下一步」段(文档注释同步) |
| `agentLoop.ts` | 新增 `NEXT_STEP_TITLE = "### 下一步"`、`buildNextStepSection(pending)`(去空白、≤3 条、空则返回 `""`);`buildTaskAnchor(todoBlock, mapLines, pendingTodos)`;`injectTodoIntoMessages` 新增 `opts.pendingTodos`;调用点传 `this.todo.list().filter(i => !i.done).map(i => i.content)` |
| `contextCompactor.ts` / `configuration.ts` / `project-overview.md` | 文档注释中「目标/已做/结果/下一步」→ 去掉「下一步」并说明由任务锚注入 |

## 二、第九轮附带修复:续写提示污染需求轨

**现场证据**:本轮采样时,实时任务锚里地图 `**最新要求**` 行内容竟是
`[续写] 上一轮输出因长度上限中断…` —— 即 `maxTokensContinue` 注入的运行时合成 user 消息。

**根因**:`contextManager.ts` 抽轨时对**任意** user 文本都 `demands.push`;
而续写提示正是以 `{ role:"user", content: kMaxTokensContinueUserText }` 落盘(`agentLoop.ts`)
→ 进需求轨,并顶掉地图「最新要求 / 下一步」位,**反过来加重目标语义污染**。

**修法**(`contextManager.ts`):
- `isRuntimeContinueMessage`(判 `[续写]` 前缀)入轨前 `continue`;
- `INTERRUPTED_ASSISTANT_TEXT`(`[输出中断]`)不参与结论/解释轨;
- `isRuntimeSyntheticText` 在 `buildResidentMap` 重建地图时**剔除历史遗留**的污染条目
  (累积式会「粘住」旧条目,必须显式过滤 —— 否则旧会话的 `[续写]` 行会一直留在「近期需求」段)。

**测试**:`contextManager.test.ts` 增 2 例(续写提示不得出现于块、地图最新要求须为真实最后需求、
历史遗留污染条目被剔除)。

### 二补:第 40 轮补漏 —— 前缀感知判定 + 地图全来源过滤

**现场证据**:实施后实时任务锚里,地图「近期需求」**和「下一步」两段都仍残留** `[续写] …` 行。

**根因(两处)**:
1. **判定漏判**:历史落盘的轨行形态是 `- [rN] [续写] …`(带编号前缀),
   而旧 `isRuntimeSyntheticText` 只 `startsWith("[续写]")` → **匹配不到**,污染行被放行。
   更隐蔽的是 `extractMapSectionItems` 会剥掉 `- ` 但仍留 `[rN]`,正则若强制要求 bullet 前缀同样漏判。
2. **过滤不全**:`buildResidentMap` 里 `goal / latestGoal / olderMiddle` 直接取自 `parts.demands`,
   上一版只过滤了 `prevRecent`(累积段)→ 污染行经 `mergeCompactedTracks` 持久化在需求轨,
   会继续占据「目标 / 最新要求 / 近期需求 / 下一步」位,反过来**污染目标语义**。

**修法**:
- `isRuntimeSyntheticText` 改为**前缀感知**:先剥 `[-*] ` 与 `[rN] `(二者均**可选**)再判前缀;
- `buildResidentMap` 对 `demands` 及 `latest()`(ledger/conclusions 来源)统一 `.filter(!isRuntimeSyntheticText)`,
  覆盖地图**全部五个段**的所有来源。

**测试**:`contextManager.test.ts` 再增 1 例 —— 轨行形态 `- [rN] [续写] …` + 裸 `[输出中断]` 的
demands/conclusions/prevMap 三来源同测,断言三形态均被剔除、真实需求仍在。

**生效时机**:旧会话**已落盘**的压缩块地图段不会被原地改写;`buildResidentMap` 只在**下一次压缩**时
用当前轨道重建 → 重载窗口后再次触发压缩,残留行即清。

## 三、阶段 C(96k / 3:7)预算实测结论

用户把历史预算改为 **96K、3:7 开**(compacted : tail),自 2026-09-14 23:01:40 起,
并要求记录时间点、后续统计是否加剧。采样于同日 23:46,与阶段 B(64K、.56/.44)**同一会话自然对照**。

### 关键数据(每轮)

用 `effCostIdx = input + 0.1×cacheRead + output`(缓存感知成本指数):

| 指标(每轮) | 阶段 B(64K,.56/.44) | 阶段 C(96K,.30/.70) | 变化 |
|---|---|---|---|
| avgInput(cache miss,最贵) | 2444 | 3561 | **+45.7%** |
| avgCacheRead | 44380 | 60088 | +35.4% |
| avgOutput | 830 | 1677 | +102% |
| **effCostIdx** | **7712** | **11242** | **+45.8%** |
| 约合 $/round(Sonnet 3/15/0.3) | 0.0331 | 0.0539 | **+62.9%** |
| 请求 avgTotal | 34239 | 53054 | +55% |
| 请求 **avgTail** | 16427 | 35337 | **×2.15(主因)** |
| 请求 avgBlock | 15649 | 15311 | −2% |
| compaction / 千轮 | 81.4 | 41.5 | **−49%** |
| 压缩自耗 token/轮 | 12 | 25 | +13 |

### 结论

1. **token 消耗确实加剧**:每轮成本 +45.8%(成本指数)/ +62.9%($)。
2. **主因是 tail 变长**:3:7 把 tail 触发点 21120 → 50400,每轮多带 2.15× tail;
   compacted 目标虽降到 14400,实测块基本持平。
3. **收益是压缩频率减半**(81.4 → 41.5 次/千轮),但压缩本身极便宜(12→25 tok/轮),
   **省下的抵不上每轮多带的 tail**。
4. **最大不确定项是 output 翻倍**:更可能是任务强度混淆(B 诊断/读码,C 密集改文件),
   非参数直接导致;但 output 单价最高,放大了总成本。
5. **不可误读的口径**:`inputTokens / 用户轮` 看似减半,但同期 `rounds / 用户轮` 也从 75→28,
   需相除才可比,**不可单独采信**。

### 建议

- **口径**:以 `effCostIdxPerRound`(或 $/round)为准,勿比总和;要干净结论需
  **另起两次全新会话各跑 N 轮**同任务对比。
- **参数**:成本敏感可回 `.40/.60`(tail 触发点约 28800)折中;若以「少压缩、少漂移」为先,保持 3:7 可接受。
- **值得单独优化**:output 翻倍若确认非任务混淆,应查「tail 越长 → 模型是否输出更长」的因果。

### 测量脚本

`.dsb/docs/compaction/budget-measure.ps1` 本轮修两处:
① 新增 `effCostIdxPerRound`;② 修好 reason 分组(原取 `$_.reason` 恒空,应为 `$_.data.reason`)。

## 六、三补(2026-09-15):地图「下一步」不再冒充待办

### 现场问题

重载后的旧会话地图里出现:

```

- 实测其可达性与拦截效果(1 or 2)
- ...
```

这些条目实际上是**已实现过的建议**(P2-3 块首地图之类),却被列为"下一步"→ 语义错误,
会把**已完成**事项显示成待办,诱导模型重复劳动。

### 根因

`contextManager.buildResidentMap` 用**需求轨的较早中间需求**填 `next`:

```ts
next: latest(olderMiddle, 2),   // 历史需求 → 冒充「下一步」
```

历史需求**没有完成度信息**,而压缩块又访问不到 `TodoManager` → 块内无论怎么填都不可能
得到真实的"下一步"。这属于"用一个必然错误的来源去满足一个需要精确状态的位置"。

### 修法(方案 A:让来源与语义对齐,而非强行猜)

| 位置 | 改动 |
|---|---|
| `taskMap.ts` | 新增 `earlierDemands` 字段 + `EARLIER_DEMANDS_TITLE = "更早的需求"`;段序:…/近期需求/更早的需求/已做/结果/下一步。`next` 注释收紧为"**真实**未完成事项";新增 `next` 的 doc 警告(不得用历史需求充当) |
| `contextManager.ts` | `buildResidentMap`:`next: latest(olderMiddle, 2)` → `earlierDemands: latest(olderMiddle, 2)`;块内**不再输出**「下一步」段(文档注释同步) |
| `agentLoop.ts` | 新增 `NEXT_STEP_TITLE = "### 下一步"`、`buildNextStepSection(pending)`(去空白、≤3 条、空则返回 `""`);`buildTaskAnchor(todoBlock, mapLines, pendingTodos)`;`injectTodoIntoMessages` 新增 `opts.pendingTodos`;调用点传 `this.todo.list().filter(i => !i.done).map(i => i.content)` |
| `contextCompactor.ts` / `configuration.ts` / `project-overview.md` | 文档注释中「目标/已做/结果/下一步」→ 去掉「下一步」并说明由任务锚注入 |
