# 缓存前缀稳定性优化清单（对照 DeepSeek 缓存机制审查）

> 生成时间：2026-08-11
> 背景：针对 DeepSeek 独立缓存前缀单元机制（请求边界落盘 / 公共前缀检测 / 固定 token 间隔落盘），对照本项目 tail + 压缩的实际构造方式，逐条审查字节稳定性，给出可落地的优化顺序。
> 相关代码：`src/agent/agentLoop.ts`、`src/agent/contextManager.ts`、`src/agent/tools/todoTool.ts`、`src/agent/tools/executor.ts`、`src/agent/contextCompactor.ts`

---

## 一、缓存机制三原则（依据）

1. **完整匹配**：每条缓存前缀是独立完整单元，任何一字差异都会让该单元失效。
2. **前缀稳定**：system prompt、工具定义 JSON、历史消息字节必须跨轮稳定，才能命中。
3. **公共前缀检测**：多次请求间存在公共前缀时，DeepSeek 会将其作为独立单元落盘。

### ✅ 问题 1：todo 块在 system prompt 内 → 每次 TodoWrite 更新都是一次前缀断裂 ![已实施]

> **状态：P0 已实施（2026-08-11）**，修复方案见下。

**旧代码**（问题所在）：
```ts
const roundSystem = `${systemPrompt}\n\n${this.todo.toPromptBlock()}${modeSeg ? `\n\n${modeSeg}` : ""}`;
```

**机制分析**：
- system 属于缓存前缀的一部分（Anthropic 兼容 API 前缀 = system + tools + messages）。
- `todo.toPromptBlock()`（`todoTool.ts:38-42`）随清单状态变化：done 翻转、增删项、id 变化。
- **变化点在 system 中部** → 该轮请求与上一轮的「请求边界落盘单元」在 todo 处断裂 → **该轮 messages 全部 miss**。
- 按「公共前缀检测」：todo 之前的部分（base system + 工具定义）仍成公共前缀单元可命中 → 这就是压缩后首轮命中率 10.1% 而非 0% 的一部分来源。
- 实测 68~75% 命中率说明：大多数轮次清单没变（system 稳定），**一旦 TodoWrite 更新，下一轮就断一次**（类似小号雪崩）。

**✅ 修复（已实施，P0 完成）**：todo 块**移出 system**，改为在 messages 尾部注入（尾部变化不影响前缀）。实现见 `agentLoop.ts` 的 `injectTodoIntoMessages`：

- 唯一读 user 消息（非 tool_result）时**合并**到该 content 前（空 block 数组时前置 text block）——首轮常见路径，变化点落在消息尾部；
- **尾部为 assistant / tool_result / 空：不注入，原样返回**。绝不追加独立 user 消息（模型会把每轮清单当成「用户又发了一句」反复复述；且 tool_use 后紧跟的 user 只能含 tool_result，追加 text 会触发兼容 API 400）；
- **绝不挂 system 后缀**：todo 是会话内动态内容，任何位置进入 system（含后缀）都会使 system 字节变化 = tools + messages 前缀全 miss（规则 1 红线，2026-08-11 曾试点后缀方案后撤销）；
- **仅当清单有未完成项（`hasPending()`）才注入**：全部完成不注入，避免模型反复 TodoWrite；
- todo 状态经由 **TodoWrite 的 tool_result 传播**（`executor.ts`：add/update 后返回 `toPromptBlock()` 完整最新清单）——变更即快照，模型每条变更后都能在消息尾部看到最新状态，无需每轮注入；
- todo 每轮随请求包重新注入，不收进持久历史。

### ✅ 问题 2：压缩块重建 = 整块重写 → 这是雪崩的根源 ![已实施]

**P2 已实施（2026-08-11）** 关键落地：
> - `track()` 参数 `includeEmptyTitle`（默认 true）：压缩块 4 个 section 标题**恒输出**（空轨仅标题行），thinking 块传 false 保持旧行为 → section 边界固定，由空变非空不在块中部插入标题行。
> - 新增 `collapseTailExplanations`（只 re-summarize 最新一半/尾部，旧稳定行永不重写），`ensureBlockFits` / `ensureBlockFitsTokens` 改用之；无历史稳定段（单行/首次压缩）时 fallback 压缩整组以保证块可收敛。
> - `trimTracksToBudget` 由「按 seq 最旧删」改为「按 seq 最新（尾部）删」→ 稳定段前缀字节不变。
> - 结论：压缩块变为**只增尾部 / 只删尾部**，跨压缩轮次旧行字节恒定 → 前缀命中（根治雪崩）。

`contextManager.ts`：
- 每次 compact：`mergeCompactedTracks(prev, parts)` 重排旧行 → `buildCompactedBlock()` 重建 → **压缩块字节整体变化**（哪怕只新增一行）。
- `ensureBlockFits` 裁剪时从「解释轨最旧一半」开始摘（`contextManager.ts:447-448`）→ 中间删行。
- section 标题**非空才输出** → 某 section 从空变非空时，后面所有行号后移。

**这直接解释了「压缩后第 1 轮命中率 10.1%」**：压缩块是 messages 前缀的头部，重写 = 前缀断裂 = 雪崩。

**✅ 修复方向**（雪崩根治，改动中等偏大）：
1. **4 个 section 标题恒输出**（空 section 用占位行）→ 行位置永久固定。
2. **新增内容只追加到 section 末尾**，旧行永不重写。
3. **裁剪只删尾部**（删尾不破坏前缀）——或「稳定段 + 增量段」双段结构：旧摘要永不重写，新摘要追加，超限只裁增量段尾部。

### ✅ 问题 3：tool_result 发送前精简 = 同一内容出现两次字节形态 ![已实施]

```ts
// agentLoop.ts —— tool_result 写入 messages 前的「写前定型」
block.content = [{ type: "text", text: `${TRIMMED_MARKER}\n${plan.trimmed}` }];
```

**机制**：tool_result 先以原始形态写入 messages 并参与第 1 次发送 → 下一轮发送前被 summarize / trim 替换 → **中间消息字节变化 → 后续轮前缀断裂一次**。

**✅ 修复（已实施，P1 完成）**：**写入 messages 前就按最终策略 trim（写前定型）**，发送前 trim 只做兜底。实现见 `agentLoop.ts:784-792`：在 tool_result push 前遍历块，对 `planToolResultTrim` 判定为 `trim` 的块直接写入 `[tool-result-trimmed]` 精简形态，使该块自首次进入消息即字节恒定。
- **trim 类**：push 时同步定型，首次即最终形态，消除二次转变 ✓
- **summarize 类**（需异步 LLM 摘要，避免阻塞工具轮）：保留原文，由发送前 `trimConsumedToolResults` 兜底汇总（罕见，仅超大稀疏且规则裁剪后仍 >3000 tokens）。

### ✅ 问题 4：消费后块删除改写历史 ![已实施]

`trimConsumedToolUses` / `trimConsumedThinking` 删除**中部**已消费的块 → 后续消息整体前移 → 前缀断裂。
- 中部删除无法两全（要么删、要么保前缀）。
- **✅ 决策（P3）**：**不删中部**——已消费块保留在 messages 中部（token 成本换命中率，符合规则 5）。同时把 tool_use / thinking 的 trim 类策略前移到**写前定型**：`agentLoop.ts` 在 push 时对 trim 类块同步定型，自首次进入前缀即最终字节形态；发送前兜底对已定型块幂等 keep（`planToolResultTrim` / `planThinkingTrim` 遇标记直接 keep），不再产生「原始 → 精简」二次形态。
- **收益**：中部已消费块字节自首轮起恒定，既不删除也不改写；兜底只覆盖会话恢复（initialHistory）场景的旧数据。
