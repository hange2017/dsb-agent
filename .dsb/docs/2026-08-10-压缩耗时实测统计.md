## 三、观察与结论

1. **耗时构成**:同一压缩流程内 `durationMs` 累积(block 先完成 → thinking → tail 最后完成),组内最大值即该次流程总耗时。
2. **耗时波动大**(13.8s ~ 65.3s):长耗时集中在 **18:00 后**,此时触发时 before ≈ 53-56K(窗口已接近 150K 预算阈值),压缩动作更重,且含模型重新生成压缩摘要的时间。
3. **体感对应**:38s 平均、65s 最长的压缩窗口,与用户反馈的"卡顿感"一致。
4. **调优建议**:
   - 150K 预算下 tail 触发阈值 ≈ 39.4K,但 before 常达 53K+,触发偏晚/偏频繁;
   - 若想减少卡顿,可把 `triggerPct` 从 0.75 提到 0.85(更早触发,单次更轻);
   - 或按 README 建议将历史信息总预算提到 256K+,降低压缩频率。

## 五、压缩耗时统计口径与扩展方向(2026-08-10 晚,对接用户大策略)

### 1. 统计粒度:从「流程级」下沉到「动作级」

当前只有流程级 `durationMs`(一次压缩总耗时)。按用户策略,需**每种压缩动作分别统计**:

| 压缩动作 | 位置/触发 | 是否调用 LLM | 需要新增的耗时字段 |
|---|---|---|---|
| 解释段压缩(`summarize`) | stratify 中 classifyAssistantText | ✅ 调用 | `explainMs` / `explainTokens` |
| 压缩块超预算再摘要(`summarize`) | ensureBlockFitsTokens | ✅ 调用 | `blockResummarizeMs` / 次数 |
| thinking 压缩(`summarize`) | compressThinkingSources | ✅ 调用 | `thinkingMs` / `thinkingTokens` |
| 算法裁剪(截断最旧 tool_result) | ensureBlockFitsTokens | ❌ 不调用 | `algoMs`(纯本地计算) |
| 冷存储写入 | backfillThinkingSummaries | ❌ 不调用 | `storeMs`(落盘 IO) |

**关键区分点**:`llmMs`(模型等待,网络+服务端)vs `algoMs`(本地计算)——两者优化手段完全不同
(LLM 部分用并行/降预算,算法部分用缓存/增量)。

### 2. 压缩耗时统计字段提案(compaction 事件新增)

```ts
{
  ...现有字段(startedAt / durationMs / before / after / position / reason / budget),
  llmCalls: number,      // 本次压缩流程调用 LLM 次数(当前盲区:summarize 调用完全没记录)
  llmMs: number,         // LLM 调用总耗时(串行段累加;并行段取 max)
  algoMs: number,        // 纯本地算法耗时 = durationMs - llmMs
  selfInputTokens: number,  // 压缩自身消耗输入(所有 summarize 的 prompt 之和)
  selfOutputTokens: number, // 压缩自身输出(所有 summarize 的生成之和)
  cacheMissAfter: number,   // 压缩后首轮 miss 增量(雪崩峰值,与 provider_round 关联)
}
```

### 3. 对接 64K 基准测试(用户策略 3)

- 测试窗口锁定 **64K** 后,压缩触发更频繁(实测 64K 时 before ≈ 30-43K,远低于 150K 的 53K+),
  单次压缩更轻 → **样本密度高,小时级统计收敛快**;
- 本报告 12 次流程基于 150K 预算(18:00 后 before 常达 53K+);切到 64K 后预期:
  - 单次耗时下降(压缩输入变小);
  - 压缩次数上升(阈值 39K→16.8K);
  - **雪崩次数上升,但单次雪崩规模下降** —— 两者净效果待实测,正是 C1 成本模型要回答的问题。
- 建议 64K 测试期把 `compaction` 事件新增字段(A1)+ `provider_round.phase`(A2)一起上线,
  前 1-2 小时即可拿到「压缩真成本 + 雪崩真规模」。
