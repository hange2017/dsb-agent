## 一、当前请求结构(system + tools + messages 三段)

`src/agent/provider/anthropicMessagesClient.ts:128-135` 构造 body:

```ts
{ model, max_tokens, stream: true, system: opts.system, tools: opts.tools, messages: outbound }
```

body 字段顺序即**前缀顺序**:`system` → `tools` → `messages`。
→ **system 或 tools 任一字节变化,后面全部失效**(不是只失效自己那一段)。

### 1.1 system 段

| 项 | 现状 | 会话内字节稳定? |
|---|---|---|
| 构建时机 | `chatViewProvider.ts:365` 会话创建时调 `buildSystemPrompt()` **一次** | ✅ 稳定 |
| 含易变内容? | `memoryIndex` / `rules` / `skillList` / `projectOverview` / `dreamHint` —— 均为创建时快照 | ✅ 稳定 |
| 每轮拼接 | `agentLoop.ts:723` `roundSystem = systemPrompt + (modeSeg ? "\n\n"+modeSeg : "")` | ⚠️ **mode 非 agent 时变化** |
| todo 清单 | 已移出 system(`injectTodoIntoMessages`) | ✅ 已修(P0) |

**实测 systemTokens 中位 2,994**(部分会话 6,527)。

### 1.2 tools 段

`agentLoop.ts:743`:`tools.allToolDefs().filter((d) => isToolAllowed(mode, d.name))`

- MCP 服务器连接/断开 → `mcpServerDefs` 变化 → 工具集变化(会话内已按规则"视为只读",但真实断连会变)。

## 二、hit / miss 归因(全部历史数据,消息级严格前缀)

按"相邻两轮首个不一致位置"分类,统计每类 miss 占全部 miss 的比例:

| 类别 | 说明 | miss (tok) | 占全部 miss |
|---|---|---|---|
| **A 压缩后首轮(idx0/idx1 断裂)** | 压缩块重建 或 从头部开始错位 | **8,838,292** | **46.8%** |
| D 纯追加仍有 miss | 新内容固有成本(非缺陷) | 5,764,763 | 30.5% |
| **C 稳定期中部改写(trim)** | 已消费块被精简 → 中部断裂 | **3,674,005** | **19.5%** |
| B 压缩后更深轮(idx≥2) | 压缩副作用残留 | 605,175 | 3.2% |

全部 miss 18,882,235 tok / 全部输入 392,133,280 tok → 整体 **95.2%**(与既有基线 97.0~97.7% 同量级,差异来自样本区间)。

> D 类(30.5%)是"新增消息本身不可能命中"的固有成本,**不算浪费**。
> 真正可优化的浪费 ≈ A + B + C ≈ **13.1M tok ≈ 全部 miss 的 69.5%**。

### 2.1 决定性的分离实验:压缩块是否重建

对 665 个"压缩后首轮",按压缩块(index0 消息)hash 是否变化分成两组:

| 分组 | n | 命中率 中位 | 命中率 均值 |
|---|---|---|---|
| **压缩块字节未变**(仅 tail 变化) | 572 | **76.3%** | 52.4% |
| **压缩块字节变化**(块重建) | 93 | **0.0%** | 32.2% |

→ **压缩块一旦重建,命中率中位跌到 0**(整段 miss);未重建则仍有 76%。
**这就是"断崖"的根因**,与规则 4(压缩块只追加、只删尾)完全对应。

### 2.2 真实口径恢复曲线(官方脚本 `analyze-cache-prefix.py`)

```
压缩后第1轮  [ 12轮] 命中 106,624 / 未命中 453,297 → 19.0%
压缩后第2轮  [ 12轮] 命中 554,112 / 未命中  18,046 → 96.8%
压缩后第3轮  [ 12轮] 命中 564,224 / 未命中  16,904 → 97.1%
稳定期(4+)   [341轮] 命中 19,305,984 / 未命中 914,358 → 95.5%
其中命中率 <20% 的雪崩首轮: 10 次
```

**结论:断崖只持续 1 轮**(第 2 轮已恢复到 96.8%)。压缩块体积中位 **17,919 tok**(p90 18,000),
即每次压缩多付 ≈ 1.8 万 tok 的全额 miss(A 类 46.8% ≈ 每次压缩的块重发成本)。

### 2.3 C 类(稳定期中部改写)的定位

断裂点**距消息末尾的条数**分布:

| 距末尾 | 次数 | 占比 |
|---|---|---|
| 2~3 条 | 604 | **57%** |
| 23 条 | 436 | **41%** |
| 其它 | 23 | 2% |

断裂点消息形态 Top5:`assistant_thinking+text+tool_use`(304)、`user_text`(254)、`tool_result+tool_result`(133)、`assistant_thinking+tool_use`(120)、`tool_result`(86)。

三个来源:
1. **thinking 精简**(`trimConsumedThinking`,`agentLoop.ts:~495`)——中部原地改写 `block.thinking`,**没有写前定型**(P1 只覆盖了 tool_result)。
2. **tool_result 精简**(`trimConsumedToolResults`)——已按 P1 写前定型,但 summarize 类走 LLM、失败会下一轮重试 → 仍可能跨形态。
3. **todo 锚注入**改写尾部 user 消息字节(`merged.push({role:"user", content: anchor+"\n\n"+content})`)——
   实测 user_text 断裂 297 轮 / miss 251,737 tok(占比小但纯属机制性浪费)。

## 三、提升方案(按投入产出比排序)

### P0 — 高收益、低风险

**① mode 段从 system 移出(体系性,影响最大)**
- 现状:`roundSystem = systemPrompt + modeSeg`(`agentLoop.ts:723`);plan/ask 模式多一段文本 → **system 变长** → tools + 全部 messages miss。
- 修复:mode 说明作为**独立消息追加到 messages 尾部**(或恒定占位),system 恒等于 `systemPrompt` 字节。
- 同理 `tools` 数组:`isToolAllowed(mode)` 过滤会让 tools JSON 变化。建议 **tools 恒为全量**,改由 messages 尾部说明当前模式可用的工具,硬拒仍在执行层(`isToolAllowed` 保留做执行门禁)。
- 收益:消除"切模式 → 全断"这一类(未单独量化,但属体系性缺陷)。

**② thinking 精简改为写前定型(对齐 P1)**
- 现状:thinking 精简在"发送前"原地改写已入历史的消息 → 该消息之后全部断裂。
- 修复:与 P1 相同——在 **push 进 messages 前**就决定 thinking 的最终字节形态(按是否超出保留窗口预定型);发送前只做兜底同形态转换。
- 收益:C 类(19.5% miss)的主要部分,估算 2~3M tok。

**③ 降低压缩频率(直接减少断崖次数)**
- 实测:压缩事件 1,354 次 / 稳定轮 8,193 → **平均每 ~6 轮压缩一次**;`budget.total` 中位 64,000。
- 而 `contextWindowTokens()` 默认 **600,000**,`triggerRatio` 默认 0.75。
- 修复:把 `historyTokenBudget` 从 64,000 提到 **150,000**(记忆中的既有目标值)→ 压缩次数约降 2.3 倍,断崖次数同比减少。
- 注意:单次压缩后 miss 只持续 1 轮(见 2.2),所以"次数减半"直接等价于"总雪崩成本减半"。

**④ 压缩块只追加不重写(P2,进行中)**
- 现状:工作区已有未提交改动(`collapseTailExplanations` / `track` 标题恒输出 / `trimTracksToBudget` 改删尾部),但 **2.1 实测仍有 93 轮块重建 → 中位 0%**。
- 关键:定位"块字节变化"的 93 次为何变化。头号嫌疑是 `mergeCompactedTracks(prev, parts)` **把新行按 seq 插入到旧行中间** → 中间插入导致其后全部前移。
- 修复方向(规则 4 已给出):**稳定段 + 增量段双段结构** —— 旧块原文作为稳定段**永不重写**,新摘要**只追加到末尾**,超限**只裁增量段尾部**。

### P1 — 中等收益

**⑤ todo 锚注入避免改写已发送消息**
- 现状:尾部是 string user 时 `anchor + "\n\n" + content` 就地改写;若该 user 消息上一轮已发送过 → 断裂。
- 修复:若尾部 user 消息**已在上一轮发送过**,改为 `push` 一条新的 user 消息(纯尾部追加);否则沿用现有就地合并(首轮路径无历史,无害)。

**⑥ 压缩块预算/tail 比例调整**
- 实测预算中位:compacted 36,000 / thinking 0 / tail 28,000(56% / 0% / 44%)。
- 压缩块中位 17,919 tok,已接近 36,000 上限的一半 → **块内裁剪(re-summarize/truncate)触发频率**值得统计;每次裁剪都是块内字节变化 → 断裂。
- 建议:压缩块预算适度上调,减少"因触顶而裁剪"的次数。

### P2 — 借鉴官方 harness(deepseek-harness)

抓取官方仓库(12,944 文件)后,与本问题直接相关的设计:

| 官方 note / 包 | 内容 | 对我们可借鉴处 |
|---|---|---|
| `bug-fix/2026-07-21-compaction-summary-prefix-cache-reuse` | **摘要调用回放对话前缀以复用 KV Cache** | 我们 `summarizeMessages`(`agentLoop.ts:448`)只发 `[message]` 单条 user + 独立 system → **不复用任何前缀**。可改为把待压缩内容作为对话 messages + 复用对话 system,压缩自身成本可降。 |
| `architecture/2026-08-25-sparse-first-party-prompt-section-orders` | 段序集中分配 + 同 order 按**名称**确定性 tie-break,避免激活顺序影响前缀 | 我们 system 段顺序已是固定数组拼接(稳定),但插件/MCP 工具序依赖注册顺序 → 应改为**确定性排序**。 |
| `feature/2026-09-02-in-history-system-prompt-replacement` | 不在请求头重发 system,而在历史里替换 | 与我们规则 1 同向;他们的做法是"system 作为 surface 节点,替换只影响替换点之后"。 |
| `packages/compaction/compaction-tool-result-pruner` | 工具结果剪枝做成独立可插拔 compaction 包 | 与我们 `planToolResultTrim` 同构;其 pruner 在**压缩阶段**集中做,而非发送前改写 → **与我们的 P0② 一致**。 |
| `architecture/2026-08-19-projection-cache-per-session-files` | 会话级投影缓存落盘 | 避免每轮重算导致字节抖动。 |
| `feature/2026-08-19-high-cache-hit-decimal-display` | 高命中率小数位显示 | 说明官方确实以 >99% 为目标,但其 99% 是**稳定期**口径;压缩后同样会跌。 |

**结论:官方 99% 的核心不是"神奇压缩",而是三条我们已知但未全部落地的纪律:**
1. **前缀永不重写**(in-history replacement + 段序确定性排序);
2. **压缩/剪枝集中在压缩阶段做,不在发送前改写历史**(tool-result-pruner 独立成包);
3. **摘要调用复用对话前缀**(我们完全没做)。

## 六、口径修正:真正的「块重建」只占 0.8%,但根因已锁定(2026-09-15 补测)

### 6.1 口径修正

上表 A 类(46.8%)混入了两类不同事件,必须分开:

| 事件 | 性质 | 计数 |
|---|---|---|
| **会话首次压缩**(index0 从普通消息变成压缩块) | 固有成本,不可优化 | 多数 |
| **真正的块重建**(前后 index0 都是压缩块,但字节变了) | **缺陷** | **91 / 11,644 = 0.8%** |

**只统计「前后轮 index0 都是压缩块」的相邻对**:

```
总对数 11,644
  块字节未变     11,553 (99.2%)
  块字节变化(true rebuild)  91 (0.8%)   中位 14,398 tok / 合计 1,357,486 tok
```

→ P2(`bb64a7d`) 的效果比初判好得多:**块本身已高度稳定(99.2%)**。

### 6.2 但 91 次重建的分布暴露了 P2 之后引入的**新**回退源

按日统计 91 次重建:

| 日期 | 08-09 | 08-10 | 08-11 | 08-12 | 08-13 | 08-15 | 08-19 | 09-14 | 09-15 |
|---|---|---|---|---|---|---|---|---|---|
| 重建数 | 24 | 16 | 2 | 7 | 1 | 21 | 3 | 1 | **16** |

**09-14/09-15 两天的压缩对全部是「块重建」,「仅 tail 变」为 0** —— 而这两天正是
`493285b`(常驻任务地图)上线之后。

### 6.3 根因:任务地图位于压缩块**首段**,且每轮用**滑动窗口重建**

`contextManager.ts:459` → `buildResidentMap(purged, prev?.map ?? this.residentMap)`;
`contextCompactor.ts:393` → `...(parts.map ?? [])` 紧跟在 `[compacted]` 之后(**块内最前缀位置**)。

`buildResidentMap`(`contextManager.ts:805`)里三段是**滑动窗口**,每次压缩都变:

```ts
did:     latest(parts.ledger, 3)        // 最新 3 条 → 滑动
results: latest(parts.conclusions, 3)   // 最新 3 条 → 滑动
earlierDemands: latest(olderMiddle, 2)  // 滑动
```

**而压缩块是单条消息(atomic)** → 块内**任一字节**变化 = 该消息 hash 变 = **整块 17,919 tok 全额 miss**。

> 这是"变化点必须尽量靠后"原则的直接违反:**最易变的内容被放在最前缀的位置**。
> 地图放在块首的本意是"永不裁剪",但它同时把"每轮都变"带到了前缀头部。

### 6.4 附带发现:地图被重复投递

任务锚每轮已通过 `getResidentMap()` 把同一份地图注入到**消息尾部**
(`agentLoop.ts:718` → `injectTodoIntoMessages(..., { mapLines })` → `buildTaskAnchor`)。
→ 地图同时存在于 **块首(前缀)** 与 **尾部锚(尾)** 两处:**尾部那份是缓存友好的,块首那份是杀手**。

## 八、T4 决策:不实施(压测后净亏,收益天花板 0.06%)

**结论:官方 harness `compaction-summary-prefix-cache-reuse` 不适用于本仓库,已决定放弃(t57 关闭)。**

### 8.1 我们与官方的前提不同(这是结论反直觉的根因)
- 官方场景:摘要调用原本发送**全量对话 transcript**(无缓存结构)。改成「回放对话前缀」后,
  `head` 从 miss 价变 hit 价 → **纯省**。
- 本仓库场景:摘要调用发送的是**已抽取的 explanation 摘录**(中位 **323 tok**),不是全量原文。
  回放前缀等于把「发摘录」换成「发原文 + 指令」→ **输入 token 净增**。
- 实测比值:`head` 中位 **29,767 tok** / `payload` 中位 **323 tok** = **92x**。
  → 同一个设计,在"本来就发全量"的架构里是省钱,在"已经抽取成摘录"的架构里是加钱。

### 8.2 量化(17 天 stats;75 次可与 compaction 配对的摘要调用)
| 方案 | 成本 | 相对现状 |
|---|---|---|
| 现状(只发摘录,全 miss) | $0.0810 | 1.00x |
| 回放(head 全命中 0.02x) | $0.0654 | **0.81x**(理论上仅小胜) |
| 回放(head 未命中 1.0x) | $2.1698 | **26.8x**(灾难性反噬) |

- 收益绝对额:$0.0156 / 17 天 ≈ **全库 miss 成本($27.55)的 0.056%**(约万分之五)。
- 风险:回放要真正命中,必须保证 system + tools + head **三段字节完全同源**;
  任一环节不一致即退化为 26.8x。而我们的 `summarizeMessages`(`agentLoop.ts:469-495`)
  用的是独立 system(`rules` 文案)与 `tools: []` → **本身就不同源**,
  要落地就得把压缩调用重构成"复用对话 system + 全量 tools + head 原文"的**架构级改动**,
  却只换来 0.056% 的收益上限。

### 8.3 价值盘子对照(为什么它注定是噪声)
全库(17 天)miss 成本 $27.55 的构成:

| 项 | 金额 | 占比 |
|---|---|---|
| 压缩后首轮断崖 | $11.01 | **40.0%** |
| 稳定期其余 miss | $16.54 | 60.0% |
| └ 其中压缩自身调用(T4 的作用对象) | $0.19 | **0.70%** |

→ T4 只能碰那 0.70%,收益上限 0.056%。
**同等投入放到「降低压缩频率」(用户计划 80K → 150K 历史预算)可省约 $6.31
≈ T4 上限收益的 124 倍。** 因此 T4 正式关闭,优先级让位于预算调整与 T3 类断崖治理。

### 8.4 附带发现 → 转为 T5 候选(零风险,且独立于 T4)
核算过程意外发现一个**真实且与 T4 无关**的浪费:**压缩摘要调用在为空转 thinking 付费**。
- `summarizeMessages` 把 `prepared.thinkingBudgetTokens` 原样透传给 provider,
  而"总结成 800 tok"这类摘要任务不需要推理预算。
- 证据(17 天,口径 = `provider_round{phase:"compact"}`):
  - 压缩调用 **282 次**;输入合计 **193,809 tok**($0.19),输出合计 **225,543 tok**($0.45)
    → **输出成本是输入的 2.33x**。
  - 真实输出 **225,543** vs 本地估算(被采用的摘要文本)**174,115**
    → **差额 51,428 tok(29.5%)= $0.10 是返回后未被采用的 token**(thinking 等)。
  - 输出分位:p50=643 / p90=1375 / p99=3207 / max=6711;其中 **99 次**落在 801~3,500(疑似 thinking 档)。
  - 用途拆分:**explanation 541 次**、thinking 6 次、resummarize/oversize 0 次。
- 候选做法:压缩调用传 `thinkingDisabled: true`(client 已支持,发 `thinking.disabled`)。
- **前置风险**:推理专用模型可能不接受禁用 thinking → 必须以能力位守卫,否则 400。

### 8.5 T5 已核算并升级为 P0(见专文)
后续核查推翻了 8.4 的「浪费」定性,并发现比金额更重的隐患:

- **定性修正**:不是新设计缺陷,而是 **`a5c857a` 移除全局 thinking 总闸时的回归**
  ——`1ea650a` 的总闸曾隐式让压缩调用不带 budget;移除总闸时未补回「压缩不需要 thinking」语义。
- **协议违规** 🔴:压缩三类调用 `maxTokens` 被钳到 800/200/3500,而 budget 仍透传 4096
  → **`budget_tokens >= max_tokens`,违反 Anthropic 硬约束**;失败会被 `catch` 静默降级为兜底文案
  → 压缩块变空(丢失任务地图与历史结论)。
- **用户侧误导** 🔴:settings 现存 `dsbAgent.thinking.enabled=false` 是 **死键**
  (`a5c857a` 已从 package.json 移除,全库无读取点);用户以为已关 thinking,实际全链路已重开。
- 金额仍极小(压缩未采用输出 ¥0.10 = 总支出 0.19%),但上述属**正确性/可观测性**风险,
  且修复成本极低(一处规则),故列为 **P0**。
