## 〇、用户观察与结论

**观察**:每轮发送任务后,agent 完成的**子任务数量异常膨胀**;怀疑与「任务地图」上线有关;
并举例:只发了「我现在重启了」这类**状态汇报**,agent 却去跑了大量 git 相关任务。

**结论**:**成立**。任务地图引入后,「短消息 → LLM 轮次」中位数从 **5 轮 → 56 轮**(≤15 字消息口径)。
根因是任务地图的 5 个机制缺陷叠加,形成一个**自我强化循环**:agent 的旁白被当作「结果」喂回自己,
把「继续推进」写进每一轮锚,使一个纯状态汇报被解读为「继续未竟的 git 任务」。

## 二、根因(5 个机制缺陷,逐条对齐代码)

### 🔴 缺陷 1:`goal` 取 `demands[0]` 且首条永久免裁 → 目标永不跟进

```ts
// contextManager.ts buildResidentMap
const goal = demands[0];                                  // ← 永远是会话第一条用户消息
// pickTrimVictim:软保护开时 slice(1, len-keepTail),首条永不进入候选 → 永不删
```

会话一旦从「完成git处理」开始,该句就是**永久目标**,即便它早已完成。跨会话恢复同理。

### 🔴 缺陷 2:需求轨无「完成态」→ 已完成事项长期滞留

`demands` 只记录 user 文本,没有任何「已办结」标记;`conclusions`/`ledger` 与之无关联判定。
于是「编译并安装当前项目」完成后仍留在 `近期需求`,`A. 从 settings 清理` 亦然。

### 🔴 缺陷 3:`conclusions` 轨吞掉一切短助手文本 → 旁白变「结果」回喂

```ts
// contextCompactor.ts classifyAssistantText
if (len < shortThreshold) { conclusion.push(trimmed); return; }   // 有工具时阈值 300 字符
```

**任何一个 <300 字符的助手文本都被判为「结论」**。agent 每轮的过渡旁白
(「先取证,不臆断」「继续推进」)因此进入 `conclusions` 轨 → `buildResidentMap` 的
`results: latest(parts.conclusions, 3)` → 下一轮锚的 `### 结果`。这是**自我强化循环的入口**。

### 🔴 缺陷 4:`ledger` = 原始工具履历 → 锚在宣称「工作正在进行」

`did: latest(parts.ledger, 3)` 取最近 3 条工具履历(含 `Read: ...` / `Bash: cd ...`)。
它向模型传达「你刚在做这些事」,配合 `结果` 里的旁白,足以让一个状态汇报被读成「继续干活」。

### 🔴 缺陷 5:`TASK_ANCHOR_HINT` 无条件前置 → 每轮都说「继续推进」

```ts
// agentLoop.ts
export const TASK_ANCHOR_HINT =
  "〔任务锚〕按下面清单继续推进;需要更早的历史原文时,用 ContextRecall(seq=n) 回查…";
// buildTaskAnchor:`${TASK_ANCHOR_HINT}\n${mode}${next}${map}${todoBlock}`
```

该句**字节恒定、每轮注入**。它把「按清单继续推进」设成常驻指令 —— 只要地图里还有
任一条未消解的 `近期需求`,模型就会去推进它。**没有「本轮只是状态汇报」的出口**。

### 附带缺陷 6:地图仅在压缩时重建 → 压缩之间持续陈旧

`residentMap` 只在 `compact()` 内(`contextManager.ts:483`)与 `seedResidentMap()` 更新。
两次压缩之间,目标/已做/结果**不刷新**,陈旧窗口可达数十轮。

## 三、自我强化循环(核心)

```
        用户发「现在重启了」(纯状态汇报)
                  │
                  ▼
   锚注入:目标=完成git处理 + 近期需求3条 + 已做=git命令 + 结果=上轮旁白
                  │   「按下面清单继续推进」
                  ▼
        模型判定:还有未竟工作 → 跑 git 调查(数十轮)
                  │
                  ▼
       输出旁白(「继续…」「剩 N 项」)→ classifyAssistantText
                  │   <300 字符 → conclusions 轨
                  ▼
        下次压缩/重建地图:结果段 = 这些旁白
                  │
                  └──────── 回到锚注入,循环放大 ────────┘
```

**闭环的关键**:模型自己的输出(旁白)经 `conclusions` 轨 → 地图 `结果` 段 → 锚 → 模型自己。
信息不外部注入,循环不衰减,反而因 `近期需求` 的累积式粘滞(`accumulateRecentDemands` 只在
超过 3 条时淘汰最旧)而**越滚越大**。

## 四、修复方案(按优先级)

### P0 — 切断自我强化循环(收益最大、风险最小)

1. ✅ **已实施(P0-1)** **`conclusions` 轨只收「真结论」,不收过渡旁白。**
   在 `classifyAssistantText` 的短文本分支加判定:若该助手消息**伴有 tool_use**
   (即本轮还要继续动作),其短文本视为**过程旁白**,不进 `conclusions`(或降入 `explanations`)。
   仅当**无 tool_use 的终答**才进 `conclusions`。
   → 直接消灭「结果段 = 我的旁白」这一入口。

2. **地图 `### 结果` 段改用「机制化事实」而非助手文本。**
   如改用工具执行的**结构化结果摘要**(成功/失败 + 文件路径 + 关键行),或干脆去掉该段。
   退一步:至少排除旁白类文本(与 P0-1 联动)。

3. ✅ **已实施(P0-3)** **`TASK_ANCHOR_HINT` 改为条件化。**
   无 pending 待办 **且** 无未消解需求时,输出中性提示(如「如无明确指令,请仅回应本轮消息」),
   而非「按下面清单继续推进」。

### P1 — 修正目标陈旧与需求滞留

4. **`goal` 改为「最近一次显式任务」**:取需求轨最后一条**被识别为任务指令**的项,
   而非 `demands[0]`。或给 goal 加**时效**:当 `最新要求` 与 goal 语义无关时,goal 让位。

5. **引入需求「消解」标记**:凡 `TodoWrite` 中 done 翻转、或被某轮终答明确覆盖的需求,
   从 `近期需求` 移除;`近期需求` 只在**存在对应未完成待办**时展示。

6. **`近期需求` 去掉累积式粘滞**:`accumulateRecentDemands` 的 `prevRecent` 叠加是
   「已完成事项永驻」的直接来源;改为只取**当前活跃**需求窗口。

### P2 — 降低陈旧窗口

7. **地图在非压缩轮也刷新**(轻量重建,不落盘块),缩短陈旧窗口。
   ⚠️ 注意缓存前缀:地图只走**消息尾部锚**,刷新不影响前缀(这是 T1 已确立的边界)。

### 可选 — 提供逃生阀

8. 设置项 `dsbAgent.compaction.taskMapEnabled` 已存在(默认开);
   建议补充「地图段开关」(仅关 `结果`/`已做` 段),便于快速降噪。

## 五之二、实施记录(P0-1 / P0-3,2026-09-16)

### P0-1 — `classifyAssistantText` 过程旁白降级(`src/agent/contextCompactor.ts`)

两处收口:

1. **短文本分支**:`hasToolUse && !hasStructuralBlock(text)` → 进 `explanation`,否则结论。
   - `hasStructuralBlock` = 含标题/列表/代码/表格块 → 那是**交付物**,仍judge结论;
   - 无结构块的短旁白(「先取证,不臆断」/「收到」)→ 说明轨(仍可 ContextRecall 回查)。
2. **首/尾段自动判结论**改为仅终答轮生效:`isEdge = !hasToolUse && (idx===0||idx===n-1)`。
   - 过程轮的开场铺垫/过渡旁白不再自动进结论轨;**含结论关键词**(结论/方案/决定/推荐/
     建议/总结/summary/…)的段落仍判结论 —— 补了原列表缺失的「总结」。

### P0-3 — 锚提示条件化(`src/agent/agentLoop.ts`)

- 新增 `TASK_ANCHOR_HINT_IDLE`(无未完成待办时的中性提示:明确「不要自行继续历史任务」);
- `buildTaskAnchor` 按 `pendingTodos` 非空 **或** 清单含 `- [ ]` 选择提示语;
- 保留 `TASK_ANCHOR_HINT` 原文(有活时语义不变,避免既有缓存前缀失效)。

### 现场自证

实施过程中,**任务锚被系统原样注入了会话上下文**:

```
### 结果
- 我的建议：**先做 P0-1 + P0-3**（切断闭环 + 提示条件化）…
- 收到，按建议实施 P0-1（切断闭环）+ P0-3（提示条件化）…
```

这三行正是「模型自己的旁白经 `conclusions` → 地图 `结果` → 锚 → 回喂自身」的**完整闭环样本**,
也正是 P0-1 要拦的对象。同轮 `**目标:** 完成git处理` 仍陈旧 → 缺陷 1 待 P1 处理。
