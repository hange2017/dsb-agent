# 压缩质量抽查(compaction_qa)的目的与意义

> 生成时间:2026-08-11
> 来源:DSBAgent 会话内关于「压缩质量抽查 token 占比」提问的分析结论
> 主题:说明 `compaction_qa` 抽查机制要回答什么问题、让我们知道什么,以及它如何服务于缓存前缀稳定与压缩正确性两条主线。

## 一、抽查机制概述(what it does)

压缩发生时,压缩块会把一大段历史消息替换成 `[compacted]` 摘要(带 `[r{n}] 序号`)。`runCompactionQa`(见 `src/agent/agentLoop.ts`)在每次压缩后做一次质量抽查:

1. 从被压缩掉的 `[r{n}]` 序号里**随机挑一个**;
2. 把压缩块全文 + 一个问题发给 provider:**「[r{seq}] 对应的原始内容是什么?」**;
3. 模型能凭摘要回答出来(`answerable=true`)→ 摘要**留住了关键信息**;
   若回答 `UNKNOWN` 或为空 → 该信息在压缩时**丢失了**。

抽查是**独立**的 provider 调用——不打 `onProviderRound`,token 只记在 `compaction_qa` 事件上,聚合时**单列扣减**,不混入真实对话轮次的 token 统计。

## 二、要回答的核心问题(the question)

> **「压缩之后的摘要块,是否还保留了让后续对话继续完成任务所需的关键信息?」**

## 三、它让我们知道什么(final purpose)

抽查不是装饰性指标,它直接服务于「缓存前缀稳定性」和「压缩正确性」两条主线:

1. **压缩不能只求「变小」,还必须「不失真」**
   把几十轮历史压成一段摘要,若摘要把错误/结论/定位等关键信息丢掉,后续模型会「失忆」出错。抽查把「压缩正确性」从无法验证的假设,变成**可量化的正确率**(answerable)。

2. **压缩逻辑改动的回归网**
   在改压缩策略时(如 todo 移出、tool_result 写前定型、压缩块 append-only),需要知道改动后是否把信息压丢。`answerable` 序列就是答案——某版本后若明显下降,说明该版压缩过度。

3. **识别「哪些信息压缩最容易丢」**
   `answerable=false` 的 seq 分布(结论 / 错误详情 / 工具履历 …)能告诉我们各类内容的保留优先级,指导裁剪策略(哪些必须保留、哪些可裁)。

4. **给「压缩到底省不省」一个诚实回答**
   压缩省下的 token 与抽查花的 token 对比——若抽查发现大量 `UNKNOWN`(信息丢失),说明压缩虽然省 token 但牺牲了正确性,这个 trade-off 需要被暴露。

## 四、对「抽查 token 占比高」的一个说明

抽查占比高(在某段时间内 in+out 口径可达 60% 量级)**本身不是浪费**——它是在为「压缩块质量」付费做监控。只要:
- `answerable` 保持在较高水平;
- 压缩能显著降低前缀 token;

这笔抽查成本就是保证「压缩而不失真」的必要监控开销。若 `answerable` 长期偏低,则说明该调低压缩激进程度,而不是削减抽查。

## 五、后续评估方向

- 统计一段时间内 `compaction_qa` 的 `answerable` 分布与趋势;
- 分析 `answerable=false` 的 `[r{n}]` 类型(结论 / 错误 / 工具履历)以指导保留优先级;
- 结合压缩省下的 token 与抽查成本,评估压缩净收益。

## 六、抽样评估结论(2026-08-11,13:00-14:42)

### 整体质量:中上,可保持

| 指标 | 数值 |
| --- | --- |
| 抽查总数 | 37 次 |
| **answerable(信息保留成功)** | **32 / 37 = 86.5%** |
| 信息丢失(answerable=false) | 5 次(13.5%) |
| 平均压缩率(out/in) | 69.4%(约压掉 1/3) |

**结论**:压缩后仍有约 **87%** 的关键信息能被摘要还原。对于"把一整段历史压成摘要"而言,该保留率**可以接受但不算优秀**,压缩质量处于健康区间,无需紧急回调压缩激进度。

### 信息丢失模式

5 次丢失的 seq:153, 255, 331, 393, 397。

- **丢失集中在"较旧但非最早"的中后段历史**(seq 150-400),而最早的 seq(<50) 4 次抽查**全通过**(100%)。最早期历史固化保存较好,中段历史经多次压缩叠加后**信息开始衰减**。
- **压缩率不是丢失主因**:丢失的压缩率在 65-77%,与通过的(~70%)基本一致,不存在"压缩越狠丢越多"的线性关系。
- 丢失呈周期性/随机分布,未发现单一根因。

按 seq 新旧分桶:
- 新(seq<50):100% 保留(4/4)
- 中(50-200):92% 保留(11/12)
- 旧(seq≥200):81% 保留(17/21)

### 评估结论

- **✅ 质量良好,暂不需要动作**:87% answerable ≥ 健康线(建议 ≥80%),本会话压缩无系统性失效;样本 37 次跨 1.5 小时,足以给出稳定判断。
- **⚠️ 关注点(非阻断)**:
  1. 中后段历史信息衰减(seq≥200 降至 81%)——属"多次压缩叠加"的信息损耗,符合预期。后续可考虑在压缩块中提升**结论/需求轨的保留权重**(与 P2 稳定段+增量段改造方向一致)。
  2. 5 次丢失全部发生在**同一条长会话**,说明高密度任务会话对摘要保留压力更大。
- **对"抽查成本高"的回答**:抽查占比高但**是值的**——它证明了压缩质量在健康线以上(87%),即压缩"每省 1 token、牺牲约 0.13 信息量"的 trade-off 当前**合理**。只有当 answerable 跌破 ~70% 时才需回调压缩保守度。

### 待办(后续统计具体情况后再定优化方向)

- 统计跨会话/跨天的压缩质量长期趋势(不只当天 13:00 后)。
- 定位 5 次丢失对应内容类型(结论/错误/工具履历),指导保留优先级。
- 结合压缩省下的 token 与抽查成本,评估压缩净收益。
